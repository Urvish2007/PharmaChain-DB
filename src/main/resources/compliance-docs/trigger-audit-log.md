# Rule: Tamper-evident QC audit trail (trg_audit_qc_changes / QC_Audit_Log)

Applies to: the Product_Quality_Check table, on every UPDATE and DELETE.

Whenever a finished-goods QC report's result is changed after the fact (for example, corrected
from FAILED to PASSED, or vice versa) or a QC report row is deleted, the trigger automatically
writes a row into QC_Audit_Log capturing: which report was affected, what the old and new result
values were, whether it was an update or a delete, who made the change, and when.

Nothing in the application ever inserts into QC_Audit_Log directly - only the trigger does. That
is the point: because the audit entry is generated by the database itself as a side effect of
the change, rather than by application code choosing to log it, there is no code path that can
modify a QC result without leaving a trace. This is the same principle behind FDA 21 CFR Part 11
requirements for electronic records in regulated industries: a record of who changed what,
and when, that the system itself guarantees exists rather than trusting each application to
remember to log it.

The audit trail for a specific QC report can be read via
GET /api/v1/quality-checks/products/{reportId}/audit-trail.
